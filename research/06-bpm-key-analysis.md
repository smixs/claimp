# 06. Автоматический анализ BPM и тональности (Camelot / Am)

Дата: 2026-09-15 18:20. Машина: macOS 27.0 (26A428), Xcode 26.6, Apple Swift 6.3.3 (`sw_vers`, `xcodebuild -version`, `swift --version`).
Второй тулчейн на машине: Command Line Tools, Apple Swift 6.4 (`/Library/Developer/CommandLineTools/usr/bin/swiftc --version`), SDK macOS 27.0.
Клоны: `clones/<repo>` (`git clone --depth 1`, в этот репозиторий не входят). Пробы: `probe/musicunderstanding/*`.
Все `path:line` - внутри клонов или внутри SDK по абсолютному пути.

Задача: BPM и тональность (Camelot 8A и/или Am) для электронной музыки и DJ-миксов, офлайн,
< 5 с на 5-минутный трек на M-серии, лицензия результата - Apache-2.0.
Решение владельца (`DECISIONS.md` 2026-09-15 18:00): чужой GPL/AGPL-код не копировать и не переводить построчно,
только как справочник алгоритмов по публикациям; своя реализация на vDSP допустима.

## 0. Главный вывод

**В macOS 27 появился системный фреймворк `MusicUnderstanding`, который считает и BPM, и тональность on-device.**
Он есть в SDK на этой машине, собирается, работает при полностью отключённой сети, укладывается
в 1,1-3,9 с на трек 2-6 минут (60-126× реального времени) и на четырёх сверенных треках дал
те же значения, что каталоги Tunebat и SongBPM (три ключа из четырёх - точно).
Лицензии нет вообще: это системный API, как AVFoundation.

Цена: `@available(macOS 27.0, *)`. У Claimp сейчас `platforms: [.macOS(.v26)]` (`Package.swift:11`).
То есть либо поднять планку до macOS 27, либо на macOS 26 колонки BPM/Key остаются пустыми
(поведение уже описано решением 17:57 «нет тега = пусто»).

Готовой permissive-библиотеки, которая делает то же самое, нет. Всё зрелое - GPL/AGPL
(aubio, libKeyFinder, MiniBPM, BTrack, Essentia, Mixxx). Из MIT есть один живой кандидат
на темп - BTT (`Beat-and-Tempo-Tracking`, реализация метода Percival & Tzanetakis 2014),
на тональность permissive-библиотеки не нашлось вообще.

## 2. Apple `MusicUnderstanding` - что проверено пробой

### 2.1 Что это и где лежит

`/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/MusicUnderstanding.framework`
(SDK `DisplayName: "macOS 27.0"`, `SDKSettings.json`). В SDK Xcode 26.6 (`DisplayName: "macOS 26.5"`) этого фреймворка нет -
проверено `ls .../MacOSX.sdk/System/Library/Frameworks | grep -i musicund` (пусто).

API по `Modules/MusicUnderstanding.swiftmodule/arm64e-apple-macos.swiftinterface` (236 строк, `-user-module-version 13`):

```swift
@available(iOS 27.0, macOS 27.0, tvOS 27.0, watchOS 27.0, visionOS 27.0, *)
public actor MusicUnderstandingSession {
    public convenience init(asset: any AVAsset & Sendable) async throws
    public convenience init<Provider>(audioProvider: Provider) where Provider: AsyncSequence,
        Provider.Element == AVReadOnlyAudioPCMBuffer, Provider.Failure == Never
    public func analyze(for analysisTypes: Set<AnalysisType>) async throws -> SessionResult
    public func cancel() async
}
public struct RhythmResult { let beats: [CMTime]; let bars: [CMTime]; let beatsPerMinute: Float? }
public struct KeyResult    { let ranges: [RangedValue<KeySignature>] }   // KeySignature = (tonic, mode)
```

- `AnalysisType`: `.rhythm`, `.key`, `.structure`, `.pace`, `.loudness`, `.instrumentActivity` (`:26-32`).
- `KeyResult.Tonic` - 17 имён (`aFlat, aSharp, a, bFlat, b, c, cSharp, d, dFlat, dSharp, eFlat, e, f, fSharp, g, gFlat, gSharp`),
  `Mode` - `major | minor`. То есть энгармонические пары приходят обеими записями, сворачивать в 12 классов нам.
- Тональность отдаётся **по временным диапазонам** (`ranges`), не одним значением: на всех проверенных треках (18 разных файлов) диапазон был ровно один, на весь трек.
- `beatsPerMinute` - **опционален**; помимо BPM есть полная сетка `beats` и `bars` (для будущей сетки на волне).
- Ошибки: `sessionInProgress, emptyAnalysisSet, invalidAsset, hasProtectedContent, internalError` (`:105-111`).
- Импортирует `CoreML` (`:7`) - под капотом модель, отсюда и «on-device».
- Есть потоковый вход `audioProvider` из `AVReadOnlyAudioPCMBuffer` - совместим с нашим `PCMReader` (мы уже читаем чанками по 10 с).

**Грабли сборки (проверено):** SDK macOS 27 требует тулчейн Swift 6.4, а `xcode-select -p` указывает на Xcode 26.6 (Swift 6.3.3).
Сборка обычным `swiftc` падает: `error: no such module 'MusicUnderstanding'`, а с явным `-sdk` на SDK 27 -
`failed to build module 'Swift'; this SDK is not supported by the compiler`. Собирается только так:

```
/Library/Developer/CommandLineTools/usr/bin/swiftc -O -parse-as-library \
  -sdk /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk \
  -target arm64-apple-macos27.0 -swift-version 6 probe.swift -o probe
```

То есть **до перехода на фреймворк придётся обновить Xcode** (в текущем Xcode ни SDK, ни компилятора нет).

### 2.2 Скорость и память (замеры `/usr/bin/time -l`, `probe/musicunderstanding/probe2`)

| Вход | Тип анализа | Время | Реальное время / расчёт | Пик RSS |
|---|---|---|---|---|
| 14 треков 2:00-4:25 (mp3 320) | rhythm+key | 1,10-3,78 с на трек, 28 с на все 14 | 60-126× | - |
| первый запуск процесса | rhythm+key | +8 с на первом треке (10,69 с при 350 с аудио) | 33× | - |
| 20:00 (mp3) | rhythm+key | 40,3 с | 30× | 611 МБ |
| 20:00 | только rhythm | 34,9 с | 34× | 400 МБ |
| 20:00 | только key | 8,3 с | 145× | 50 МБ |
| 60:00 | только rhythm | 85,7 с | 42× | 326 МБ |
| 60:00 | только key | 25,5 с | 141× | 50 МБ |
| 60:00 | rhythm+key | 87,9 с | 41× | **1,06 ГБ** |
| 60:00 | rhythm+key, первый холодный прогон | 204 с | 18× | не снят |

Выводы из замеров:
1. **Цель «< 5 с на 5-минутный трек» выполняется с запасом**: худший из 14 треков - 3,78 с, типичный - 2 с.
2. **Дорогой - ритм, а не тональность.** `key` линеен и дёшев: 145× реального времени на 20 минутах,
   141× на часе, 50 МБ на любой длине. Весь остальной расход - `rhythm`.
   Цена секунды аудио для `rhythm+key` не постоянна: 113× реального времени на четырёхминутном треке,
   30× на двадцатиминутном, 41× на часовом. То есть короткие треки обходятся втрое дешевле в пересчёте
   на секунду, а дальше кривая выравнивается.
3. Первый вызов в процессе на ~8 с дороже (загрузка модели), а самый первый прогон за сессию был дороже в 2,3 раза
   (204 с против 87,9 с на повторе того же файла) - анализ надо ставить в фоновую очередь одним долгоживущим
   процессом/актором, а не дёргать на каждый клик.
4. **Память - главный риск.** На часовом файле `rhythm+key` взял 1,06 ГБ (больше суммы раздельных прогонов:
   326 МБ + 50 МБ), то есть типы анализа считаются параллельно и каждый держит свой буфер. Два-три часовых микса
   одновременно съедят всю память. Значит: очередь с жёстким ограничением параллелизма и, возможно, раздельные
   вызовы `.rhythm` и `.key` вместо одного общего.
5. Часовой микс - это полторы минуты, а не секунды. Для тридцати- и шестидесятиминутных миксов
   (бриф 02: «Треки 30-60 минут») нужен фоновый анализ с прогрессом, а не блокирующий вызов.

### 2.3 Точность на корпусе владельца

Корпус: `~/Music/deemix`, 155 файлов, жанры из тегов - Dance/Electro (38 из первых 60 - `TAG:genre=Dance`), по сути drum & bass.

**Тегов в корпусе почти нет** (проба `ffprobe` по всем 155 файлам, `evidence/bpm-key/tags.tsv`):
- `TBPM/BPM/tmpo` - **3 файла из 155**;
- `TKEY/KEY/INITIALKEY/©key` - **0 файлов из 155**.

То есть колонки «BPM/тональность из тегов» (решение 17:57) на этой фонотеке будут пустыми в 98 % строк -
это и есть практическое обоснование анализа.

Сверка Apple с эталонами (три - теги самого файла, четыре - каталоги):

| Трек | Эталон BPM / ключ | Источник эталона | Apple | Итог |
|---|---|---|---|---|
| Unglued - Deep Dark and Dirty | 172 / - | тег `TBPM` файла | 172,00 / f minor | BPM точно |
| Foreign Concept - Ask Yourself | 170 / - | тег `TBPM` файла | 85,00 / f minor | BPM ровно вдвое меньше |
| Vromm - Level Up | 170 / - | тег `TBPM` файла | 85,00 / g minor | BPM ровно вдвое меньше |
| Bensley - Hit The Lights | 86 / E minor | Tunebat (страница Beatport по прямому запросу отдала 403) | 86,00 / e minor | **BPM и ключ точно** |
| Camo & Krooked - Sunglasses At Night | 87 / Eb minor | Tunebat (страница Beatport по прямому запросу отдала 403) | 87,00 / eFlat minor | **BPM и ключ точно** |
| BUNT. - TRIPPIN | 175 / D major | SongBPM | 87,50 / d major | ключ точно, BPM вдвое меньше |
| Arcando - California Dreamin' | 175 / F# minor | SongBPM | 87,50 / cSharp minor | BPM вдвое меньше, ключ на квинту (класс ошибки «fifth») |

Что из этого следует:
- **Ключ: 3 совпадения из 4, четвёртое - ошибка на квинту** (в MIREX такая ошибка оценивается как частично верная).
  Это соответствует уровню коммерческих инструментов; выборка из 4 треков мала, шире не проверялось.
- **Тон-октава - главная проблема, и она не только у Apple.** Каталоги сами не согласны между собой: Tunebat
  для этих D&B-релизов даёт 86-87, SongBPM для других треков того же корпуса - 175, теги deemix - 170-172. Apple выбирает
  «половинный» вариант на 5 из 7 сверенных треков.
- В научной литературе это известный класс ошибок: у Percival & Tzanetakis (TASLP 2014, табл. II, 4011 треков)
  точный Accuracy 1 базового варианта - **52,4 %**, а Accuracy 2 (с допуском на кратность 1/3, 1/2, 1, 2, 3) - **91,4 %**.
  Оракульное «удваивать или нет» подняло бы Accuracy 1 с 52 % до 85 %. То есть **угадать октаву труднее, чем найти период**.
- Практический вывод для нас: показывать BPM с пользовательским диапазоном (как в Mixxx), например 85-170 или 90-180,
  и удваивать/делить результат на границе диапазона. Сетку `beats` при этом надо прореживать/уплотнять синхронно.

### 2.4 Что ещё проверено

- **Офлайн**: `sandbox-exec -f nonet.sb` с профилем `(allow default) (deny network*)` - результат бит в бит тот же
  (`Bensley - Hit The Lights`: `bpm=86.00 key=e minor`, 2,31 с). Сеть не нужна.
- **Форматы**: один и тот же трек в mp3, FLAC, WAV, AAC (m4a) и ALAC (m4a) даёт **одинаковый** результат
  (`86.00 / e minor`) - декодирование берёт на себя AVFoundation.
- **Невалидный вход**: текстовый файл и битый m4a → `MusicUnderstandingError.invalidAsset`. Ошибка явная, тихого нуля нет,
  под наше правило «no fallbacks, fail fast» ложится напрямую.
- **Подпись/энтайтлменты**: проба - неподписанный ad-hoc бинарник, работает. Поведение внутри App Sandbox не проверялось (нам он и не нужен: Claimp раздаётся через Developer ID DMG).
- **Нестабильность на неритмичном материале**: на часовом эмбиенте без выраженной доли `beatsPerMinute` между прогонами
  менялся (36,29 / 45,06 / 49,41). На ритмичных треках повторные прогоны давали одинаковые значения.

## 3. Сторонние библиотеки: что смотрел в коде

- **aubio** (`clones/aubio`): `src/tempo/*` - 1129 строк, метод Davies & Brossier; БПФ - свой `ooura` по умолчанию,
  опционально FFTW3 или Accelerate (`wscript:55-60,97`). Лицензия GPL-3 (`COPYING:1`). Как код не годится.
- **libKeyFinder** (`clones/libkeyfinder`): 2510 строк, хромаграмма на 72 полосы (6 октав × 12),
  `KeyClassifier` сравнивает с тон-профилями мажора и минора (`src/keyclassifier.cpp:26-37`),
  **обязательная зависимость FFTW3** (`CMakeLists.txt:31-32`). GPL-3 плюс лицензия FFTW - двойной запрет.
- **MiniBPM** (`clones/minibpm`): один `src/MiniBpm.cpp` + заголовок, API `setBPMRange(min,max)` / `estimateTempoOfSamples`
  (`src/MiniBpm.h:53-110`) - ровно та форма, что нам нужна, но GPL-2.
- **BTT** (`clones/Beat-and-Tempo-Tracking`, MIT): `src/` 3794 строки ANSI C, без внешних зависимостей, свой DFT (`src/DFT.c`).
  В README прямо названы источники: темп - Percival & Tzanetakis 2014 (`README.md:190-191`), бит - диссертация Adam Stark 2011 (`:276-277`).
  Диапазон по умолчанию 50-200 BPM, есть подавление гармоник лог-гауссовым весом вокруг 120 (`BTT.h:62-73`).
  Библиотека **причинная/реалтаймовая**: для офлайнового анализа всего трека надо отключить затухание гистограммы
  (`btt_set_gaussian_tempo_histogram_decay(1.0)`, README `:248`).
- **madmom**: исходники BSD-2, но веса моделей - CC BY-NC-SA 4.0 (`LICENSE:46-70`, «If you want to include any of these files
  ... in a commercial product, please contact ...»). Для Apache-2.0 продукта модели непригодны, а без них код - пустая оболочка.
- **Essentia**: AGPL-3 (`COPYING.txt:1`, README). Алгоритмы по документации: `RhythmExtractor2013` («beat positions ... and tempo in bpm»),
  `PercivalBpmEstimator` («estimates the tempo in beats per minute»), `KeyExtractor` («extracts key/scale») поверх `HPCP`.
  Профили `edma`/`bgate` - из работ Faraldo и др. (ECIR 2016 «Key Estimation in Electronic Dance Music»; AES 2017 «A multi-profile method for key estimation in EDM»).
  Сами профили - это опубликованные таблицы чисел из статей, не выражение кода Essentia.

## 4. Юридическая граница (кратко, по источникам)

Источник: GNU GPL FAQ (`https://www.gnu.org/licenses/gpl-faq.html`), Apache-2.0, тексты лицензий в клонах.

1. **Построчный перевод GPL-кода на Swift - нельзя.** GPL FAQ, «What does the GPL say about translating some code to a different
   programming language?»: *«Under copyright law, translation of a work is considered a kind of modification. Therefore, what the GPL
   says about modified versions applies also to translated versions.»* Перевод `MiniBpm.cpp` или `keyclassifier.cpp` в Swift = производная работа = GPL.
2. **Реализация по опубликованной статье - можно.** Copyright защищает выражение, а не алгоритм; статьи Percival & Tzanetakis 2014,
   Ellis 2007, Faraldo 2016, диссертация Stark 2011 открыты. Практическое правило для исполнителя: писать по статье, GPL-исходник
   в это время не открывать, в коммите ссылаться на статью, а не на файл GPL-проекта. Прецедент у нас уже есть:
   `Sources/Waveform/BandSplitter.swift:22-33` - взяты порядок и границы полос из Mixxx, код не копировался, это записано в комментарии.
3. **Вызов GPL-бинарника отдельным процессом (например, CLI `aubio`).** GPL FAQ относит `pipes, sockets and command-line arguments`
   к «communication mechanisms normally used between two separate programs» (раздел про aggregate), а разделы про Emacs и интерпретаторы
   подтверждают, что копирайт инструмента не покрывает то, что через него прогоняют. То есть **запускать** aubio из Claimp формально можно,
   но: (а) сам бинарник тогда надо распространять по GPL-3 отдельно и с исходниками, (б) в DMG под Developer ID это лишние 10-20 МБ,
   подпись чужого бинарника, нотаризация и апдейты, (в) пользователю придётся его ставить. Практически - худший вариант из трёх.
4. **Apache-2.0 и GPL.** GPL FAQ не содержит отдельного пункта про Apache 2.0 и GPLv2/GPLv3 (проверено чтением страницы) -
   утверждение о совместимости беру не из FAQ, а из практики: Apache-2.0 код можно включать в GPLv3-проект, но не наоборот;
   то есть **вставить GPL-код в Apache-2.0 проект нельзя ни в какой форме**, кроме смены лицензии всего Claimp на GPL-3.
5. **LGPL-путь не рассматривался**: среди кандидатов LGPL-библиотеки с нужной функцией не нашлось.
6. **Camelot.** Само колесо и обозначения `8A/8B` - система Mixed In Key; таблица «тональность → код» используется в rekordbox,
   Serato и Traktor. Юридический статус обозначения как товарного знака **не установлен** - см. открытые вопросы.

## 5. Три варианта и рекомендация

### Вариант 1 (рекомендуемый) - Apple `MusicUnderstanding`

**Что делаем:** таргет `platforms: [.macOS(.v27)]` (или `if #available(macOS 27, *)`), новый модуль `Sources/Analysis`,

  и `structure` (интро/дроп - то, ради чего владелец просил «видно развитие трека»).
- Минусы: macOS 27 (на macOS 26 функции нет), нужен Xcode с SDK 27 и Swift 6.4, поведение - чёрный ящик,
  октавную неоднозначность всё равно чинить самим.
- Объём: ~150-200 строк своего кода (обёртка, кэш, Camelot-таблица, диапазон BPM) + колонки в таблице.

### Вариант 2 (запасной) - своя реализация по статьям на vDSP

Берётся, если владелец не готов поднимать планку до macOS 27.

- Темп - Percival & Tzanetakis 2014 (см. план в §6.2), тональность - хрома + профили EDMA/bgate (Faraldo 2016).
- Плюсы: работает на macOS 26, лицензия своя, всё на vDSP поверх уже написанного `PCMReader`/`BandSplitter`.
- Минусы: 600-900 строк нового DSP-кода плюс тесты; ожидаемое качество - хуже Apple; по табл. II статьи
  точный Accuracy 1 базового варианта 52 %, с допуском на кратность - 91 %.
- Объём: 2-3 дня работы исполнителя плюс корпус для проверки.

### 6.2 Вариант 2 - темп по Percival & Tzanetakis 2014 на vDSP

Все параметры ниже - из статьи (IEEE TASLP 22(12), 2014, §II), не из чужого кода.

1. **Onset Strength Signal.** Вход 44 100 Гц моно. Окна 1024, хоп 128 → `F_sO = 344,5` Гц (§II-A-1).
   Окно Хэмминга, `L_P(k,n) = ln(1 + 1000·|X(k,n)|)` (ф. 1), спектральный поток по `N = 513` бинам
   только с положительным приращением (ф. 2), бин 0 выбрасывается. Затем FIR 14-го порядка, срез 7 Гц (§II-A-4).
   На vDSP: `vDSP_DFT_zrop_CreateSetup` + `vDSP_vsub`/`vDSP_vthr`/`vDSP_sve`, FIR - `vDSP_desamp` (уже используется в проекте).
   ~120 строк.
2. **Период доли.** Кадры OSS по 2048 отсчётов (≈5,94 с), хоп 128 (≈0,37 с) (§II-B).
   Обобщённая автокорреляция `A(t) = DFT⁻¹(|DFT(OSS)|^c)`, `c = 0,5`, с нулевым дополнением вдвое (ф. 3).
   Усиление гармоник `EAC(t) = A(t) + A(2t) + A(4t)` (ф. 5). Берём 10 пиков в пределах
   `min_lag = 98`, `max_lag = 414`, что соответствует 50-210 BPM (ф. 6-7). ~150 строк.
3. **Оценка кандидатов импульсными поездами.** Для кандидата `P` и фазы `φ` строим три последовательности
   `I_{P,φ,v}`, `v ∈ {1; 1,5; 2}`, `B = 0..3`, веса 1,0 / 0,5 / 0,5 (ф. 8), кросс-корреляция с OSS по всем фазам (ф. 9),
   две оценки: максимум и дисперсия по фазам (ф. 10), нормировка по кандидатам и сумма (ф. 11), `argmax` (ф. 12). ~150 строк.
4. **Накопление по треку.** На каждый кадр в аккумулятор кладётся гауссиана `μ = L_m`, `σ = 10` в области лагов (ф. 13-14),
   в конце - пик аккумулятора, `BPM = 60·F_sO / L` (ф. 4). ~60 строк.
5. **Октава.** В статье базовый вариант без коррекции даёт Accuracy 1 = 52,4 %; порог «удваивать ниже 71,9 BPM»
   (`stem-heur`) даёт 78,0 % на кросс-валидации. Нам SVM не нужен: берём пользовательский диапазон (§6.1 п.5). ~40 строк.

**Тональность (вариант 2).** Хрома из того же спектра: 12 классов, логарифмический биннинг по частоте с A4 = 440,
свёртка по октавам 2-6, нормировка по кадру, усреднение по треку (медиана устойчивее среднего).
Классификация - корреляция круговых сдвигов профилей мажора и минора (Krumhansl-Schmuckler), профили брать из
опубликованных таблиц: Krumhansl & Kessler 1982, Temperley 2001 и EDMA/EDMM из Faraldo 2016 (для электроники профили
из EDM-корпуса дают заметно лучший результат, чем классические). ~200 строк. CQT не нужен: наш `BandSplitter`
уже показывает, что биквады на vDSP дают нужное разрешение дешевле.

Итого варианта 2: ~700-800 строк нового DSP-кода.

## 7. Тестовый план

1. **Синтетика (детерминированная, в репозитории).** Генератор в тесте: клик-трек ровно на 128,0 / 174,0 BPM
   (импульсы + шум), синус-аккорды A-C-E (Am) и C-E-G (C) по 8 тактов.
   Ожидание: BPM в пределах ±1 %, тональность точно. Это happy-path-шов, 2 теста.
2. **Провальный шов.** Тишина 30 с и белый шум 30 с: не падать, вернуть «не определено» либо явную ошибку;
   молчаливого 0 BPM быть не должно (правило `no fallbacks, fail fast`).
3. **PBT** (`swift-property-based` уже в зависимостях): на `TempoOctave` - для любых `bpm > 0` и диапазона `[lo, 2·lo)`
   результат лежит внутри диапазона и отличается от входа только степенью двойки; на `MusicalKey` - roundtrip
   `Camelot ↔ (tonic, mode)` и «12 классов × 2 лада = 24 разных кода».
4. **Реальный корпус - вне репозитория, скриптом в `.scratch`.** Эталоны:
   - 3 трека с тегом `TBPM` из `~/Music/deemix` (170, 170, 172) - уже выписаны в `evidence/bpm-key/tags.tsv`;
   - расширить: прогнать по всем 155 файлам и сложить в TSV, сверить «сколько треков дали BPM в диапазоне 165-180 после октавной коррекции»;
   - публичные размеченные наборы для электроники, если владелец согласится их скачать: **GiantSteps+ EDM Key Dataset**
     (Zenodo, 600 двухминутных фрагментов с разметкой тональности) и GiantSteps Tempo. Это стандарт сравнения для EDM;
     скачивание = отдельное разрешение владельца (глобальное правило «ничего не качать без явного слова»).
   - **Не годится как эталон:** публичный Deezer API - поле `bpm` вернуло `0` на всех 13 найденных треках корпуса (проверено).
5. **Скорость.** Гейт: 5-минутный трек < 5 с (сейчас 2 с), часовой микс - отдельная планка, согласовать с владельцем.
6. **Регресс на форматах.** Один трек в mp3/FLAC/WAV/m4a: результаты должны совпасть (сейчас совпадают).
